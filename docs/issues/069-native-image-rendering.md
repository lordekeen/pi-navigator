## Description

The #057 chafa tier renders images as ANSI symbol art: terminal-agnostic but low-fidelity, dependent on an external binary, and a subprocess per render. Both the #057 spec (§16 item 1) and the implementation plan (§8 item 1) deliberately left the native tier unshipped pending a spike: *does a pi-tui image render correctly inside an overlay region?*

The spike is now substantively answered — verified 2026-09 against pi-navigator v0.7.4, pi-tui 0.85.1, pi 0.86.1, chafa 1.18.2, and tmux 3.7c:

- **pi-tui already ships the native layer**: `Image`, `renderImage`, `encodeKitty`/`encodeITerm2`, `getCapabilities`/`setCapabilityOverrides`, kitty metadata/placement/crop helpers, and both renderers' kitty lifecycle (reserved rows, changed-range expansion, per-ID deletion). pi core renders its own image content through it.
- **pi's extension loader aliases `@earendil-works/pi-tui` to the host singleton**, so an extension shares capability state (including the user's `terminal.images` override) — the dual-instance hazard pi-chafa documents does not apply to a TS-source extension.
- **Headless overlay probe passed**: a pi-tui kitty line survives the navigator's `hardTruncate` + `padTo` + `compositeTuiLine` byte-identically; metadata registration intact.
- **pi-chafa's native path is not reusable code**: it emits image content blocks rendered by the host's `ToolExecutionComponent`; it never writes protocol bytes, and has no sixel support.

This issue delivers the **native tier** per [`docs/specs/native-image-rendering.md`](../specs/native-image-rendering.md): it activates the reserved `imageTier: "native"` and makes the ladder **native → chafa → metadata**, opt-in via an extended `images.mode` (`off | chafa | native | auto`). Sixel stays out (upstream pi-tui proposal); chafa native formats stay out (unmanaged streams).

## Proposed Approach (summary; the spec is authoritative)

- **Reuse, never re-encode**: `runNativeRender` reads a bounded file, base64s it, calls pi-tui `renderImage` (+ `allocateImageId` for kitty), and builds rows with the same layout as pi-tui's `Image.render` (kitty: sequence + empty filler; iTerm2: fillers + `moveUp + sequence`). No protocol bytes are generated by pi-navigator.
- **Capability ladder (instance-independent)**: `getCapabilities().images` → settings `terminal.images` (`"kitty"|"iterm2"` only) → `PI_IMAGE_PROTOCOL` → null; positive-only, mirroring pi-chafa's `resolveCapsImages`.
- **Modes**: `off`/`chafa` unchanged; `native` strict (kitty/iTerm2 only, card + hint otherwise); `auto` = native → chafa → card, honoring pi-chafa `preferNative` (new mirror field) and `CHAFA_PREFER_NATIVE`. `PI_NAV_IMAGES` keeps its byte-compatible truth table plus `native`/`auto` tokens.
- **Mime gate**: kitty → PNG only (pi-tui sends `f=100`; no converter dependency); iTerm2 → PNG/JPEG/GIF/WebP; other formats fall back per mode.
- **Bounds**: `IMAGE_NATIVE_MAX_BYTES = 4 MiB`; native cache entries over `IMAGE_NATIVE_CACHE_MAX_CHARS = 1M` chars display but are not retained (the 16-entry viewer cache is not a byte bound).
- **Rows/chrome**: native rows are emitted verbatim (`""` fillers), never width-processed; `isImageLine`-aware pass-through in the frame/join path; the image is paned to the geometry, scroll pinned.
- **Cleanup**: primary is the host renderer's line-diff deletion; a dispose-time kitty delete is contingency only if live QA shows ghosts.
- **No tmux wrapper**: inherit pi-tui's tmux/screen `images: null` behavior and the host override semantics; document the limitation.

## Open Questions

1. **Filler-row accounting under overlay compositing** — the compositor pads filler rows with spaces, so pi-tui's `getKittyImageReservedRows` sees a single-row image. Image anchoring still works headlessly, but live redraw/scroll behavior must be judged; mitigations (image-aware compositing, upstream exception, single-row sizing) are listed in spec §16 item 1.
2. **tmux passthrough** — pi-tui emits no DCS envelope; a wrapper is future work. Note the user's tmux 3.7c advertises `sixel_support=1`, which keeps sixel attractive there.
3. **Sixel** — tracked upstream (pi-chafa's pi-tui proposal); slots into the ladder if `ImageProtocol` grows.
4. **Oversized images** — 4 MiB cap means some photos fall back; revisit only if pi exposes a public resize API.
5. **`terminal.imageWidthCells`** — native currently uses the full pane width; decide during QA whether to honor the host width preference.
